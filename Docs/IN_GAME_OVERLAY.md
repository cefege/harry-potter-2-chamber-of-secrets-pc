# Experimental in-game overlay shell

The `hp2-engine` Cargo feature `in-game-overlay` is **off by default**. Do not enable it in a user build until user-facing runtime verification exists. No retail package or game data change is needed.

With the feature and SDL enabled, F10 opens or closes the shell; Escape closes it. Up/Down select an action and Enter activates it. The shell does not pause the game. It does not change mouse capture. Focus loss closes the shell before the existing release-all sequence. Releases for presses previously forwarded to gameplay pass through; overlay-owned and unmatched releases are suppressed, including after the menu closes. Focus loss retains release ownership until release or a fresh press. The shell cannot be opened during an engine replay or recording.

## Provider boundary

`hp2_engine::in_game_overlay::set_content(viewport, Content)` publishes a snapshot for an opaque live viewport identity. `Content` contains a title, status lines, and `Action` records with stable IDs, labels, and enabled flags. Poll `take_action(viewport)` on the engine thread to receive an activated ID. The provider publishes Display and Performance categories. Display toggles the live `UClient::ShowFPS` flag only after configuration publication succeeds. Performance changes stored VSync and frame-limit values only; both require restart and do not change runtime objects. Enter cycles supported values. Unknown or missing stored values disable the relevant control rather than being overwritten silently. A failed save displays an error and leaves runtime state unchanged. Changing page resets selection to the first row.

## Not wired or verified

No launcher settings integration, pause, mouse navigation, controller navigation, localization, or runtime feature switch is connected. Only FPS, VSync and frame-rate limit are wired; VSync and frame-rate limit are restart-only. Core stages its system cache and detects external modifications, but external writers must be serialized: the conflict check cannot close the check/rename race. Publication can also flush unrelated pending changes already in the system cache. The page refreshes on input, not continuously, so another subsystem changing the flag can leave the displayed value stale until the next input. 

## Categories and pointer navigation

Canvas draws Display and Performance categories without another UI stack. Back returns to the category list; page changes reset focus to the first row. The shell has no scrolling, focus restoration per category, or control types beyond activation.

Mouse navigation is not implemented. SDL reports absolute pointer positions only when the mouse is not grabbed, while gameplay commonly grabs it; the current overlay deliberately leaves grab and cursor state untouched. `hp2-platform` has a separate default-off `overlay-mouse` feature with a disconnected `capture_arbitration` seam and checked SDL adapter. It tests request ordering, cursor restoration and failure rollback with a fake host; it is not a proven process-wide owner. With `overlay-mouse`, the physical SDL pump now offers an `UpdateInputBackend::observe_focus_gained` callback before legacy grab restoration, even when no grab was previously lost. The callback defaults to no action; replay and deterministic verification do not invoke it. Game capture, focus, overlay, teardown and every viewport must use one arbiter before connection. SDL cursor and relative mode are process-global, while window grab is per-window; multi-viewport ownership and actual SDL failure/rollback behavior need real-window tests. A safe implementation needs a shared draw/hit-test layout using the same Canvas origin, clipping, UI scale and DPI conversion, plus explicit grab/cursor release and restoration on close, focus loss, teardown and errors. It also needs press/release ownership so clicks and held gameplay inputs do not leak across transitions. Test those paths and real window focus with both data profiles before exposing pointer controls. These are gaps, not functional controls.

SDL viewport destruction removes the address-keyed state at `destroy_sdl_viewport` in `crates/hp2-engine/src/platform_owner.rs`, before fallible teardown. A unit test covers removal and address reuse; an actual SDL destruction/recreation lifecycle has not been runtime-verified. Providers must stop publishing content for a viewport when it is destroyed, or they can recreate stale state. The active Canvas small font must exist. Rendering and actual focus/input behavior have not been verified in either prototype or retail gameplay. Replay transitions, held axes and repeat behavior need runtime coverage before enabling the feature. The overlay is not an acceptance or feature-gate promotion.
